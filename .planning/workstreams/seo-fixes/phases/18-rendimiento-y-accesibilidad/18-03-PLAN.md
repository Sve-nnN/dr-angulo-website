Implementar lo que la atribución del perfilado señaló. El contrato de abajo aplica sea quien sea el culpable.

**Regla dura, sin excepción: el HTML servido de `/testimonios` sale idéntico antes y después.** Ni un nodo más, ni un nodo menos, ni una clase distinta. Con esa regla el problema del placeholder desaparece: si el marcado servido no cambia, el navegador pinta todo en el primer frame y no existe ningún momento en que algo ocupe el espacio de otra cosa. El CLS = 0 deja de ser algo que hay que cuidar y pasa a ser estructuralmente imposible de romper.

Lo que se difiere es trabajo de cliente, nunca marcado.

**Si el culpable es el JavaScript muerto de la ruta:** el objetivo es que el código del carrusel deje de descargarse y compilarse en rutas que no pueden renderizarlo, sin cambiar un solo nodo del HTML servido. Este trabajo se coordina con el plan 18-05, que es dueño del análisis del bundle: si el arreglo pasa por reorganizar el punto de importación de `ReelsCarousel`, hacerlo acá y anotarlo en el SUMMARY para que 18-05 mida sobre el resultado y no sobre la línea base vieja.

**Si el culpable es el trabajo de cliente del carrusel** (posible solo si la cuenta de Instagram se vinculó entre medio y el carrusel volvió a renderizar): el `ResizeObserver` y la primera corrida de `updateEdges()` se montan cuando la sección entra en viewport, con `IntersectionObserver`, en vez de en la hidratación; y el handler de `onScroll` agrupa sus lecturas en `requestAnimationFrame` descartando las corridas pendientes, para que un gesto de scroll produzca una lectura de layout por frame y no una por evento. El estado inicial de los botones se mantiene en `atStart` verdadero y `atEnd` falso, que es exactamente el estado que ya tienen hoy antes del primer efecto: sin cambio visual en el primer frame.

**Si el culpable es el bloque de reseñas:** el arreglo no es diferir el montaje, porque es un Server Component y no hay montaje de cliente que diferir. Sería reducir el volumen de DOM o el costo de estilo, con el mismo contrato de HTML idéntico.

Tres prohibiciones, cada una con su motivo:

1. **`dynamic(..., { ssr: false })` está prohibido.** Borra el HTML del servidor y obliga a un placeholder, que es el único camino por el que el CLS puede dejar de ser 0. Y además `InstagramReelsSection` es un Server Component `async`: la guía de lazy loading de la versión instalada de Next dice que `ssr: false` no está permitido con `next/dynamic` en Server Components. Habría que introducir un envoltorio de cliente solo para poder degradar el resultado.
2. **`content-visibility: auto` sin `contain-intrinsic-size` está prohibido.** Es la vía rápida para bajar Style & Layout y también la vía rápida para introducir CLS. Si se usa, hay que declarar el `contain-intrinsic-size` exacto por breakpoint, y ese tamaño tiene que coincidir con las alturas de la tabla del UI-SPEC.
3. **Ningún cambio visual.** El trabajo de rendimiento no tiene presupuesto visual en esta fase: los tres únicos cambios de interfaz sancionados están en el plan 18-01. Si el arreglo necesita cambiar el aspecto de algo, el arreglo está mal planteado.

**Parada obligatoria:** si el arreglo que el perfilado exige requiere `ssr: false`, o un placeholder, o el cuarto cambio visual que arrastra (fijar el título del reel a dos líneas exactas para volver determinista el alto de la tarjeta), la tarea se detiene y se sube la decisión a Juan antes de escribir una línea. El UI-SPEC deja las dimensiones del placeholder calculadas por si ese camino se aprueba: 601px de alto reservado bajo 640px y 637px desde 640px. Ese camino no está aprobado hoy.
